- 리드 초안 세 파일(`team-practices.md`, `discovered-rules.md`, `evidence.md`)을 보안 관점에서 검토했다. 근거 자료: 기술명세서 v0.2 §1.2·§2.4·§8·§10·§11.1~§11.4·§14.4, `org.md`, 타당성 제약 목록(C-R01·C-R04·C-T05), 타당성 Q5(🟡 항목 모두 확정).
- 4주 교육 과정 시연 프로젝트라는 점에 맞춰 제안 수준을 낮게 잡았다. 시연 서버 1대, 실제 아동 자료 없음(C-R01), 자동 CD 없음(§11.3)이므로 운영 서비스 수준의 보안 파이프라인(DAST 게이트, SBOM, 침투 시험)은 권하지 않는다.

### 1. 린트·포맷을 보안 게이트로 쓰는 문제

- 확정된 사실: PR마다 GitHub Actions에서 build·test·lint·ArchUnit을 실행하고, 리뷰어 1명 승인과 CI 통과 뒤 병합한다(§1.2 ✅, §11.3 🟡→Q5 확정). 이것이 이 프로젝트의 유일한 자동 보안 관문이다. 리드 초안의 "린트 실패 시 PR 차단"과 일치하며 동의한다.
- ArchUnit의 "외부 SDK 타입이 Adapter 밖으로 나가지 않는다" 규칙(§2.5)은 키·SDK 객체가 Controller 응답으로 새는 것을 구조적으로 막는 보안 통제로도 쓸모가 있다. 별도 도구를 더하지 않아도 되는 근거다.
- 한계: "아동 발화를 로그에 남기지 않는다"는 린트로 완전히 막을 수 없다. 코드 리뷰 확인 항목과 시나리오 시험으로 보완하는 편이 비용 대비 낫다(아래 5절).
- 중요한 공백: "PR 리뷰 1명 + CI 통과 뒤 병합"을 **강제**하려면 GitHub 브랜치 보호(또는 ruleset)가 켜져 있어야 한다. GitHub 무료 조직 요금제에서는 비공개 저장소에 브랜치 보호를 걸 수 없고 공개 저장소에서만 쓸 수 있는 것으로 알고 있다. 조직 요금제가 문서에 없으므로 **[미정 — 인터뷰]**: 저장소 공개 여부와 조직 요금제에 따라 이 규칙이 "도구로 강제"인지 "팀 약속"인지가 갈린다(6절과 연결).
- Java 포매터·린터는 기술명세에 없다(리드 초안과 같은 판단). 보안 관점에서는 필수가 아니다.

### 2. SAST / DAST

- 기술명세 어디에도 SAST·DAST가 없다. 새로 넣는 것은 팀 결정이므로 제안만 한다.
- SAST 선택지(인터뷰용, 기본 제안은 A 또는 B):
  - A. 추가 안 함 — 린트 + ArchUnit + 코드 리뷰로 충분하다고 본다.
  - B. GitHub CodeQL 기본 설정 — 설정 파일 없이 켤 수 있다. 공개 저장소는 무료, 비공개 저장소는 유료 기능으로 알고 있어 공개 여부에 달려 있다.
  - C. Semgrep 등 별도 도구 — 이 일정에는 과하다고 본다.
  - 어느 쪽이든 **병합 차단이 아니라 경고**로 시작하기를 권한다. 실시간 음성·AI 경험이 없는 팀(C-O03)에 오탐 처리 부담을 더하지 않기 위해서다.
- DAST: CI 게이트로 넣지 않기를 권한다. 스테이징이 없고(범위 Q6) 자동 CD도 없다. 대신 운영 단계(배포 실행·성능 검증)에서 **시연 전 1회 수동 점검**으로 대체하기를 제안한다 — `/internal/` 외부 차단(§11.1), HTTPS 동작, 세션 쿠키 HttpOnly·Secure·SameSite=Lax(§8 ✅), 개발용 CORS 설정이 시연 서버에 남지 않았는지(§11.2). 이 점검 목록 자체는 지금 정할 필요가 없고 운영 단계 산출물로 넘긴다.

### 3. 비밀 정보 관리(키는 환경 변수로만)

- 확정된 사실: OpenAI·제브·구글·VAPID 키, 내부 공유 비밀, DB 접속 정보는 서버 환경 변수로만 넣고 저장소에 넣지 않는다(§8 ✅, §11.3, C-R04). 기술명세가 AWS Secrets Manager 대신 환경 변수를 택했으므로 그 결정을 바꾸자고 하지 않는다.
- 공백 1 — 강제 장치가 없다. "넣지 않는다"는 약속만 있고 실수로 커밋되는 것을 막는 장치가 정해지지 않았다. 선택지 **[미정 — 인터뷰]**:
  - A. GitHub 비밀 스캔 + 푸시 보호 — 공개 저장소는 무료로 알고 있다.
  - B. gitleaks를 pre-commit 훅과 CI에 둔다 — 공개 여부와 무관하게 쓸 수 있다.
  - C. `.gitignore`와 리뷰만 쓴다.
  - 어느 경우든 최소한으로 권하는 것: 저장소 루트 `.gitignore`에 `.env*`(단, `.env.example` 제외)·인증서 개인 키 파일 패턴을 넣고, 변수 **이름만** 적은 `.env.example`을 둔다. 이 두 가지는 비용이 거의 없다.
- 공백 2 — CI에 비밀이 필요 없어야 한다. "CI에서 실제 유료 API를 부르지 않는다"(§10)가 지켜지면 GitHub Actions Secrets에 공급자 키를 넣을 이유가 없다. 이를 규칙으로 명시하면 CI 로그·포크 PR을 통한 키 유출 경로가 없어진다. 이것은 문서에서 **추론**한 것이므로 팀 확인이 필요하다.
- 공백 3 — Next.js 공개 환경 변수. Next.js는 `NEXT_PUBLIC_` 접두사가 붙은 환경 변수를 브라우저 번들에 넣는다. 비밀 키를 이 접두사로 두지 않는 것이 "키를 브라우저에 보내지 않는다"(§8 ✅)를 지키는 실제 방법이다. 코드 리뷰 확인 항목이나 `AGENTS.md`에 적을 만하다.
- 공백 4 — 시연 서버(EC2)에서 환경 변수 파일을 어디에 어떤 권한으로 두는지, `deploy.sh`가 어떻게 넘기는지는 문서에 없다. 지금 정할 일이 아니라 인프라 설계 단계로 넘기기를 권한다.

### 4. 의존성·공급망 점검

- 기술명세에 의존성 점검 방식이 없다. 제안(인터뷰용, 비용 낮은 순):
  - 잠금 파일 커밋: 프론트엔드 잠금 파일을 커밋하고 CI에서 잠금 파일 기준으로 설치한다. Gradle은 버전 카탈로그 등으로 버전을 고정한다. 구체 도구 선택은 개발자 판단으로 둔다.
  - Dependabot 경보: 공개·비공개 모두 무료로 알고 있다. 경보만 켜고 자동 업데이트 PR은 끄기를 권한다 — 4주 일정에서 Spring Boot 4.1 조합(§14.3 PoC)을 흔드는 자동 업데이트 PR은 오히려 위험하다.
  - GitHub Actions와 Docker 기반 이미지는 최소한 버전 태그로 고정한다(`latest` 금지). 커밋 해시 고정은 이 규모에는 선택 사항이다.
  - SBOM 생성·정기 감사는 권하지 않는다(시연 규모에 과함).
- `ai/` Python 코드는 운영 서버가 아니다(§1.2). 의존성 점검 대상에서 빼도 된다고 보지만, 공개 저장소가 되면 `ai/`에 넣는 데이터셋의 재배포 조건이 문제가 된다(6절).

### 5. 아동 발화 로그 금지

- 확정된 사실: 아동 발화 원문·전사·원음, AI 요청·응답 본문을 애플리케이션 로그에 남기지 않는다. 로그에는 sessionId를 남긴다(§8 ✅, §11.4, C-R04). 리드 초안의 NEVER 문구가 §8과 일치하며, 강한 규칙으로 두는 데 동의한다.
- 구현 때 실제로 새는 경로(지금 규칙에 덧붙일 필요는 없고, 이후 NFR 설계·코드 생성에서 확인할 항목으로 남긴다):
  - HTTP 클라이언트·SDK의 DEBUG 로그(요청·응답 본문 출력), JPA/Hibernate의 SQL 바인딩 값 로그 — 전사 저장 쿼리에 원문이 찍힌다.
  - 예외 메시지·스택 추적에 전사·AI 응답이 포함되는 경우.
  - 프론트엔드 `/device`의 브라우저 콘솔 로그 — 기술명세는 "애플리케이션 로그"만 말하므로 브라우저 콘솔이 포함되는지 문서상 불분명하다. **[미정 — 인터뷰 또는 NFR 단계]**
- 정합성 확인: §9 NFR-04는 "공급자 요청 필드 감사 로그"를 요구한다. 이 감사 로그는 **필드 이름·크기 같은 메타데이터만** 남겨야 §8 로그 금지와 충돌하지 않는다. 이 해석이 맞는지는 NFR 요구사항 단계에서 확정하면 된다. 지금 규칙 문구를 바꿀 필요는 없다.
- 검증 방법 제안: 시나리오 하네스(§10)에서 로그 출력을 붙잡아 합성 대본 문장이 나타나지 않는지 확인하는 시험 하나를 두면 이 규칙이 시험 가능해진다(inception 규칙 "요구사항은 시험 가능해야 한다"). 품질 에이전트 영역과 겹치므로 제안만 한다.
- 범위 주의: 이 금지는 **로그**에 관한 것이다. 기록 기능으로 PostgreSQL에 전사를 저장하고 EBS에 원음을 저장하는 것(§6.3)은 허용된 기능이다. 규칙 문구가 "저장 금지"로 넓게 읽히지 않게 "애플리케이션 로그"라는 말을 꼭 남겨 두기를 권한다.

### 6. 공개 저장소 여부(🟡)

- §8의 해당 행은 "**공개하면** 실제 아동 자료·전사·키·.env·개인 키·재배포 조건 미확인 데이터셋을 넣지 않는다"는 **조건부 규칙**이다. Q5로 확정된 것은 이 조건부 규칙이고, **공개할지 말지 자체는 어느 문서에도 없다**. 리드의 `evidence.md` 판단과 같다. 따라서 공개 여부를 묻는 것은 ✅ 재질문이 아니라 ⬜ 값을 정하는 것이다.
- 공개 여부가 다른 결정에 주는 영향(인터뷰에서 함께 보여 주기를 권한다):

| 항목 | 공개 | 비공개 |
|---|---|---|
| 브랜치 보호로 "리뷰 1명 + CI" 강제 | 무료 요금제에서 가능 | 조직 요금제에 따라 다름(요금제 미확인) |
| 비밀 스캔 + 푸시 보호 | 무료 | 유료 기능 — gitleaks 등 대안 필요 |
| CodeQL | 무료 | 유료 기능 |
| `aidlc/` 기록(감사 기록·질문 답변·산출물) | 함께 공개됨 | 팀 안에만 있음 |
| `ai/`·`content/`의 데이터셋·승인 문구 | 재배포 조건 확인 필요 | 문제 적음 |

- 특히 `aidlc/` 작업 공간은 프레임워크 관례상 커밋 대상이다(감사 기록, 의도 기록, 메모리 포함). 공개 저장소라면 AI-DLC에 넣은 모든 입력이 공개된다. "실제 아동 자료·키를 AI-DLC 입력에 넣지 않는다"(§2.4)가 이 경우 바로 공개 유출 방지 규칙이 된다.
- 선택지 제안 **[미정 — 인터뷰]**: A. 처음부터 공개 / B. 비공개로 개발, 시연 뒤 정리해서 공개 / C. 계속 비공개 / X. 기타.
- 공개(A 또는 B)라면 리드 초안 `discovered-rules.md`에 빠진 "재배포 조건을 확인하지 않은 데이터셋을 저장소에 넣지 않는다"(§8)를 규칙 후보로 추가해야 한다.

### 7. 합성 데이터만 쓰는 규칙

- 확정된 사실: 데모와 시험에는 합성 데이터와 성인 역할극만 쓴다(§8 ✅, C-R01). 실제 아동 개인정보 처리 의무가 이번 범위 밖이라는 전제(C-R01 영향 칸)가 이 규칙에 기대고 있으므로, 보안·규제 관점에서 **가장 근거가 강한 규칙**이다.
- 적용 범위를 분명히 하기를 권한다: 시험 대본 파일, 시나리오 하네스 입력, PoC 스크립트(`ai/`)의 평가 음성, 시연 중 녹음된 원음(EBS), AI-DLC 입력 모두 포함. 특히 PoC에서 "한국어 아동 발화 정확도"(§14.3)를 재려고 실제 아동 음성을 구하려는 유혹이 생길 수 있으므로, 이 규칙이 PoC에도 적용된다는 점을 인터뷰에서 한 번 짚어 주면 좋다(재질문이 아니라 적용 범위 안내).
- 시연 뒤 EBS 원음·DB 정리 여부는 운영 단계에서 다루면 된다.

### 8. `discovered-rules.md` 후보 분류

단계 규칙상 최종본에는 사람이 말한 강한 제약만 남는다. 기술명세의 ✅ 항목은 팀이 적은 결정이고, 타당성 제약 목록(C-R01·C-R04·C-T05)은 사람이 승인한 산출물이므로 근거가 있다. 아래는 보안 관점의 분류다. 보안과 무관한 기술 선택 규칙은 품질·개발 에이전트 판단에 맡기고 의견만 적는다.

**A. 근거가 충분한 강한 제약(보안·개인정보) — 그대로 두기를 권한다**

| 후보 | 근거 | 의견 |
|---|---|---|
| ALWAYS 키·공유 비밀·DB 접속 정보는 서버 환경 변수로만 | §8 ✅, §11.3, C-R04 | 동의 |
| ALWAYS 데모·시험에는 합성 데이터와 성인 역할극만 | §8 ✅, C-R01 | 동의. 적용 범위에 PoC 포함 |
| ALWAYS 모든 요청에서 보호자 소유 확인 | §8 ✅ | 동의. 객체 단위 접근 통제(IDOR 방지)의 핵심. 통합 시험으로 검증 가능 |

| NEVER 아동 발화·전사·원음, AI 요청·응답 본문을 애플리케이션 로그에 | §8 ✅, §11.4, C-R04 | 동의. "애플리케이션 로그" 표현 유지 |
| NEVER GPT-Live 요청에 판정 기준·라벨·확률·이전 결과·보호자 입력 원문 | §11.4, C-T05(FR-F15·NFR-04) | 동의. 최소 정보 전송 통제 |
| NEVER CI에서 실제 유료 API 호출 | §10 | 동의. 결과적으로 CI에 공급자 키가 필요 없어진다 |

**B. 근거는 있으나 문구 확인이 필요한 것**

- NEVER API 키를 브라우저에 보내지 않는다(§8 ✅): §8 원문은 "OpenAI·제브·구글·**VAPID** 키는 … 브라우저에 보내지 않는다"인데, 웹 푸시(§1.2 확정)는 구조상 **VAPID 공개 키**를 브라우저에 줘야 구독이 된다. 구글 OAuth 클라이언트 ID도 로그인 리디렉션에서 브라우저에 보인다. 글자 그대로 규칙화하면 확정된 웹 푸시 결정과 모순된다. 결정을 다시 묻는 것이 아니라 문구를 "비밀 키(OPENAI_API_KEY, JEV_API_KEY, GOOGLE_CLIENT_SECRET, VAPID_PRIVATE_KEY, INTERNAL_SHARED_SECRET)는 브라우저에 보내지 않는다. VAPID 공개 키와 구글 클라이언트 ID는 공개값이다"로 정리할지 확인하기를 권한다.
- ALWAYS PR은 리뷰어 1명 승인과 CI 통과 뒤 병합(§1.2 ✅): 결정은 확정이다. 다만 도구로 강제되는지는 공개 여부·요금제에 달려 있다(1절·6절). 규칙 자체는 유지.
- NEVER JWT 라이브러리(§8 ✅): 확정 결정이므로 근거는 충분하다. 성격상 보안 제약보다 기술 선택(Tech Stack)에 가깝다. 어느 절에 둘지는 리드 판단에 맡긴다.

**C. 리드 초안에 빠졌지만 같은 수준의 근거가 있는 보안 후보 — 넣을지 인터뷰에서 확인**

- NEVER CSRF 보호를 끄지 않는다(§8 "끄지 않는다", 🟡→Q5 확정). Spring Security 예제를 따라 하다 `csrf().disable()`을 넣는 일이 흔하다. AI 개발 도구가 이 실수를 하기 쉬우므로 규칙으로 둘 가치가 있다.
- NEVER `/internal/` 경로와 내부 WebSocket을 Nginx 밖으로 노출하지 않는다(§8, §11.1, 🟡→확정). 서버 간 인증이 공유 비밀 헤더 하나뿐이므로 이 차단이 실질적 경계다.
- ALWAYS 기기 토큰은 해시로만 저장한다(§8 "무작위 256비트, 해시 저장", ✅ 방향 / 🟡 방식).
- NEVER 시연 서버 설정에서 CORS를 허용하지 않는다 — §11.2는 "개발 환경에서만 허용"이라고 적었으므로 근거가 있다.
- (공개 저장소일 때) NEVER 재배포 조건을 확인하지 않은 데이터셋을 저장소에 넣지 않는다(§8).

**D. 보안과 무관한 관례 — 보안 관점 의견 없음**

ScriptSpeaker 경유, `contracts/` 먼저 수정, Flyway·JPA 스키마, OpenAI starter·TTS·STT 금지, openapi-typescript 생성 파일 수정 금지, EC2 Terminate 금지, 합성 결과를 실제 성능으로 보고 금지. 근거는 모두 기술명세에 있다. 강한 규칙으로 둘지 `team-practices.md`의 일반 관례로 둘지는 품질·개발 관점과 인터뷰에 맡긴다. 다만 강한 규칙이 많아질수록 각 규칙의 무게가 떨어지므로, 보안·개인정보 규칙(A·C)은 반드시 강한 규칙으로 남기기를 권한다.

### 9. 인터뷰에 더할 질문(보안, 최소 개수)

1. 저장소 공개 여부: 처음부터 공개 / 비공개로 개발 후 시연 뒤 공개 / 계속 비공개 (6절 표를 함께 제시).
2. 비밀 유출 방지 장치: GitHub 비밀 스캔+푸시 보호 / gitleaks(pre-commit+CI) / `.gitignore`와 리뷰만. (`.gitignore`·`.env.example`은 어느 경우든 권장)
3. SAST: 추가 안 함 / CodeQL 기본 설정(경고만) / 기타.
4. 의존성 점검: Dependabot 경보만 / 경보+자동 업데이트 PR / 없음. (잠금 파일 커밋은 권장)
5. 규칙 문구 확인: VAPID 공개 키·구글 클라이언트 ID를 "브라우저에 보내지 않는 키"에서 빼는 문구 정리(8절 B).
6. 8절 C의 보안 후보(CSRF, `/internal/` 차단, 기기 토큰 해시, 시연 서버 CORS)를 강한 규칙으로 둘지.

DAST, 시연 서버 환경 변수 파일 보관, 로그 경로 세부, 브라우저 콘솔 로그 범위는 이후 단계(NFR·인프라 설계·운영)로 넘기기를 권한다.

### 2. 시험 작성 시점(Methodology·Ordering) — 인터뷰에서 정할 것

기술명세는 시험 작성 시점을 정하지 않았다. org 기본값은 test-after다. 이 프로젝트의 특징 때문에 사람이 고를 만한 선택지가 셋 이상이다.

- **A. test-after (org 기본값)**: 각 계층을 구현한 뒤 그 계층 시험을 쓰고 실행한다.
- **B. custom — 상태 기계 우선 시험**: 세션 상태 전이표·연습 상태 기계·종료 처리 순서·멱등 처리(기술명세 §4)처럼 표로 이미 정의된 규칙은 구현 전에 표 기반 단위 시험을 먼저 쓰고, 나머지 계층은 구현 뒤에 쓴다. 근거: 상태 전이표가 이미 문서로 있어 시험을 먼저 쓰기 쉽고, 이 부분이 시연 실패(P2·오류 화면) 위험의 중심이다(범위 정의 "끊김 없음" 기준).
- **C. custom — 수용 시나리오 우선**: 범위 정의서가 "Must 완료 기준을 수용 테스트 기준으로 쓴다"고 했으므로(scope Q4), 시나리오 하네스 대본(Given/When/Then 형태의 인셉션 수용 조건과 대응)을 구현 전에 쓰고 단위 시험은 구현 뒤에 쓴다.
- **D. tdd / bdd / atdd 전면 적용**.

어느 쪽이든 team-practices.md에는 `Methodology`와 `Ordering` 두 필드를 명시해야 한다. B·C처럼 섞이면 `custom`으로 적어야 한다(단계 정의 Step 5).

### 3. 커버리지 하한과 측정 — 인터뷰에서 정할 것

org 기본값은 mvp 범위에 줄 커버리지 80% 하한 + 병합 전 CI 실행을 더한다. 기술명세에는 하한도 측정 도구도 없다. **[미정]** org 규칙상 Build and Test는 정한 하한을 "통과시키려고 낮출 수 없다". 따라서 아래 경계를 **지금** 정하지 않으면 구현 막바지에 하한을 지킬 수 없게 되어도 조정할 방법이 없다.

- 하한을 80%로 받아들이는가, 더 엄격하게 하는가(org 규칙상 더 낮출 수는 없다).
- 측정 단위: 백엔드 모듈별(core-api, realtime-activity, contracts) / 저장소 전체 합산 / 프론트엔드 따로.
- 측정 도구: Java와 TypeScript 각각 무엇을 쓰는가(기술명세에 없음. 예: Java는 Gradle과 붙는 커버리지 도구, TS는 Vitest 내장 커버리지 공급자 — 후보일 뿐).
- 측정에서 뺄 범위: openapi-typescript 생성 파일, `contracts/` DTO, 설정 클래스, `ai/` Python(운영 서버 아님), 가짜 모델·시험 도구 코드. 무엇을 빼는지 미리 적어 두지 않으면 "하한 낮추기"와 구분되지 않는다.
- CI에서 하한 미달이 PR을 **막는가**, 보고만 하는가.
- 줄 커버리지 외에 상태 기계 모듈에 분기(branch) 커버리지 기준을 따로 둘지(상태 전이표 누락 칸을 잡는 데 줄 커버리지보다 유효).

### 4. CI 품질 게이트 — 인터뷰에서 정할 것

확정된 것은 "PR마다 build·test·lint·ArchUnit"뿐이다. 다음은 문서에 없다.

- 어떤 수준의 시험이 PR마다 도는가: 단위·ArchUnit은 당연히 PR. Testcontainers 통합 시험(PostgreSQL·Neo4j), 가짜 모델 시나리오 하네스, 장애 주입 시험을 PR마다 돌릴지, 하루 한 번/병합 뒤에만 돌릴지. 5인 병렬 개발에서 PR 대기 시간과 맞바꾸는 결정이다.
- 계약 시험의 실행 방식: 기술명세는 "contracts/ 스키마 검증"이라고만 적었다. 어떤 형식(예: JSON Schema, 공유 DTO 직렬화 왕복 시험)으로 양쪽 서버를 검증하는지, `contracts/` 변경 PR에서 양쪽 서버 시험이 함께 도는지 **[미정]**.
- OpenAPI 명세와 생성 타입 불일치 검사 추가 여부 — 기술명세 §11.3에서 🧪. 리드 초안 Q9와 같다.
- 불안정한(flaky) 시험 처리 방침: 실시간·타이머 시험(공백 4분, 10초·30초·5초 잠정값 — 기술명세 §13, TD-09)이 실제 시간을 기다리면 CI가 느리고 불안정해진다. 시간 주입(가짜 시계) 사용을 팀 관례로 둘지, 불안정 시험을 격리·수정하는 기한을 둘지.
- 프론트엔드: Vitest 단위 시험 외에 부모 앱(/parent)·기기 웹(/device)의 브라우저 단위 끝-끝 시험을 둘지. 기술명세에는 없고 음성 수동 체크리스트만 있다. 두지 않는다면 그렇게 적어 둘 것.

### 5. 가짜 모델 시험 — 인터뷰에서 정할 것

- 가짜 GPT-Live·가짜 제브·가짜 LLM을 어디에 두는가(각 서버 시험 소스 / 공유 시험 모듈). 5인 병렬 개발에서 여러 Unit이 같은 가짜를 쓰므로 소유자를 정해야 한다.
- 가짜가 실제와 어긋나지 않게 하는 방법: PoC(10/13)와 "따로 실행하는 실제 AI 시험"에서 받은 실제 응답 형태로 가짜를 맞추는지. 실제 응답을 기록해 쓸 경우 아동 발화 원문·전사·AI 요청·응답 본문을 로그·저장소에 남기지 않는 규칙(기술명세 §8, §11.4)과 충돌하지 않게 합성 대본만 쓰는지 확인 필요.
- "실제 AI 시험"을 누가, 언제(예: PoC 뒤 / 대체 경로 결정 10/19~10/23 전 / 시연 전), 어떤 키로 실행하는지. 결과를 어디에 남기며 "합성 결과" 표기를 어떻게 붙이는지.

### 6. 수동·PoC 시험과 첫 조각 검증

- 음성 수동 체크리스트(실제 마이크·스피커)와 PoC 스크립트(`ai/`)는 CI 밖이다. 실행 시점(예: 매 Bolt 병합 뒤 / 시연 리허설 전)과 결과 기록 위치를 정해야 Build and Test가 확인할 수 있다. **[미정]**
- 테스트 계획서(기술명세 §1.3)를 누가, 어느 단계까지 쓰는지 **[미정]**. 장애 주입 AC-CON-01~10의 절차가 여기서 나오므로 구현 단계 전에 필요하다.
- 첫 조각(walking skeleton)의 검증 명령으로 "가짜 모델을 쓴 시나리오 하네스 1건이 기기 연결 → 아동 서비스 → 보호자 서버까지 통과"를 쓸지, 실제 GPT-Live 연결 수동 시연을 쓸지. org 규칙은 검증 명령이 "실제 끝-끝 결과"를 보여야 한다고 하므로, 가짜 모델만으로 충분한지 사람의 판단이 필요하다.

### 7. 시험 전략 Standard와 기술명세 §10의 관계

`aidlc-state.md`의 시험 전략은 Standard(구성 요소당 5~8개, 단위 + 통합)다. 기술명세 §10은 여기에 계약·시나리오·장애 주입을 더한다. org 규칙상 범위 하한과 시험 전략은 **더하기만** 하므로 충돌은 아니지만, Code Generation이 Standard만 보고 시나리오·장애 주입을 빠뜨릴 수 있다. team-practices.md에 "§10의 7개 수준은 Standard 전략에 더해 필수"라고 명시하기를 권한다. 전략을 Comprehensive로 올릴지는 사람이 정한다.

### 인터뷰 질문 제안 (Testing Posture)

1. 시험을 언제 쓸까요? A. 구현한 뒤(org 제안) / B. 상태 전이표처럼 문서로 정해진 규칙만 먼저, 나머지는 뒤 / C. 수용 시나리오 대본 먼저, 단위 시험은 뒤 / D. 전부 먼저(TDD 등) / X. Other (please specify)
2. 줄 커버리지 하한을 80%로 둘까요, 더 높일까요? 하한 미달이면 PR을 막을까요?
3. 커버리지를 모듈별로 잴까요, 합산할까요? 측정에서 뺄 범위(생성 코드, `contracts/` DTO, `ai/`, 시험 도구)는 무엇인가요?
4. Java와 TypeScript 커버리지 측정 도구는 무엇으로 할까요?
5. 통합(Testcontainers)·시나리오 하네스·장애 주입 시험을 PR마다 돌릴까요, 병합 뒤나 하루 한 번 돌릴까요?
6. 계약 시험은 어떤 방식으로 양쪽 서버를 검증할까요? OpenAPI 명세–생성 타입 불일치 검사를 CI에 넣을까요(🧪)?
7. 가짜 GPT-Live·제브·LLM은 누가 소유하고 어디에 둘까요? 실제 응답과 맞추는 방법은?
8. 실제 AI 시험·음성 수동 체크리스트·PoC 스크립트는 누가, 언제 실행하고 결과를 어디에 남길까요?
9. 테스트 계획서(시나리오·장애 주입 절차)는 누가, 언제까지 씁니까?
10. 타이머가 걸린 시험은 가짜 시계를 쓰도록 팀 관례로 둘까요? 불안정한 시험은 어떻게 처리할까요?
11. 부모 앱·기기 웹의 브라우저 끝-끝 시험을 둘까요, 수동 체크리스트로만 갈까요?
12. 첫 조각의 검증 명령을 가짜 모델 시나리오로 할까요, 실제 음성 연결 시연으로 할까요?

## Positions

- AGREE: 리드 초안이 Methodology `test-after`와 Ordering을 org 기본값의 **제안**으로 표시하고 인터뷰로 넘긴 것 — 기술명세가 작성 시점을 정하지 않았으므로 팀 사실로 적으면 안 된다.
- AGREE: 기술명세 §10의 7개 시험 수준·도구와 ArchUnit 규칙(§2.5)을 확정 사실로 옮긴 것 — §1.2 시험 🟡이 타당성 Q5에서 확정되었고, 프로젝트 교정 규칙상 다시 묻지 않는다.
- AGREE: "CI에서 실제 유료 API를 부르지 않는다", "합성 결과를 실제 아동 성능으로 보고하지 않는다"를 Forbidden 후보로 둔 것 — 기술명세 §10에 명시된 강한 제약이며 시험 설계 전체에 영향을 준다.
- OBJECT: 커버리지 항목의 미정 사항을 "하한과 측정 도구" 두 가지로만 적은 것 — org 규칙상 하한은 나중에 낮출 수 없으므로, 측정 단위(모듈별/합산), 제외 범위(생성 코드·`contracts/` DTO·`ai/`·시험 도구), PR 차단 여부까지 인터뷰에서 함께 정해야 한다.
- OBJECT: 시나리오 하네스 필수 사례를 "기술명세 §10" 참조로만 남긴 것 — 이 목록은 Build and Test 확인 기준이므로 team-practices.md의 Testing Posture에 사례 목록을 직접 옮겨야 추적이 끊기지 않는다.
- OBJECT: 테스트 계획서(기술명세 §1.3)가 시나리오·장애 주입 절차를 따로 정한다는 사실과, PR마다 도는 시험 수준·가짜 모델 소유·실제 AI 시험 실행 시점이 미정이라는 점이 초안 "확인할 점"에 빠진 것 — 5인 병렬 개발에서 이 공백은 Unit 사이 시험 중복·누락으로 이어진다.
- OBJECT: "선택된 시험 전략은 Standard다"를 사실로만 적고 §10과의 관계를 밝히지 않은 것 — Standard(단위 + 통합)만 보면 시나리오·장애 주입이 빠질 수 있으므로 "§10 수준은 Standard에 더해 필수"라고 명시해야 한다.

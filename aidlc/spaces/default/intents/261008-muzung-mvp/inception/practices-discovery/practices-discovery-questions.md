# 팀 작업 방식 질문 — 무중 MVP

이 파일은 팀 작업 방식(브랜치·병합, 첫 조각, 시험, 배포, 코드 스타일, 강한 규칙)을 정하는 질문과 답을 모두 기록합니다.

질문은 아래 자료를 바탕으로 만들었습니다.
- 릴리스 엔지니어의 초안(`team-practices.md`, `discovered-rules.md`, `evidence.md`)
- 품질·개발·보안 담당의 독립 검토(`contributions/`)
- 기술명세서 v0.2

이미 정해진 것은 다시 묻지 않습니다.
- 기술명세서에 확정(✅)으로 적힌 것과, 팀이 확정한 제안(🟡) 항목(타당성 Q5)은 묻지 않습니다. 예: 브랜치 `feature/{JiraKey}-설명`, 커밋 `{JiraKey} type: 내용`, PR 리뷰 1명 + CI 통과 뒤 병합, Monorepo, JUnit 5·Testcontainers·ArchUnit·Vitest, ESLint·Prettier, EC2 1대 수동 `deploy.sh`.
- 범위 정의에서 정한 것도 묻지 않습니다. 예: 운영은 시연 서버 하나, 위험 먼저 순서.

다음 항목은 해당 설계 단계에서 따로 묻습니다.
- HTTPS 방식(⬜), 인스턴스 크기(🧪), OpenAPI 불일치 검사(🧪) → 인프라 설계·CI 단계
- 가짜 모델의 담당과 위치, 테스트 계획서 담당 → 기능 설계·빌드·테스트
- Flyway 버전 규칙의 세부 → 기능 설계

각 `[Answer]:` 뒤에 고른 선택지 글자를 적고, 직접 쓰려면 `X` 뒤에 내용을 적습니다.

B. 병합 커밋(merge commit)으로 합치고, 브랜치 수명은 정하지 않는다
C. 리베이스 뒤 합친다(커밋 이력을 그대로 일렬로 둠)
D. Not yet defined

## Q6. 시험을 쓰는 시점

C. 수용 시나리오(카드의 완료 기준) 대본을 먼저 쓰고, 단위 시험은 구현 뒤에 쓴다
D. 모든 코드에 시험을 먼저 쓴다(TDD)
X. Other (please specify)

[Answer]: A

## Q8. CI에서 돌릴 시험의 범위

기술명세서는 PR마다 build·test·lint·ArchUnit을 돌린다고 적었고, 시험 수준은 단위·계약·통합·시나리오·장애 주입·음성 수동·PoC 일곱 가지입니다. PR마다 무엇까지 돌릴까요? (CI에서는 실제 유료 AI를 부르지 않는다는 원칙은 이미 정해져 있습니다)

질문 중 확인(사용자 추가 질문 "Q8 항목에 대한 설명이 필요함. B안 선택 시 AI, 음성 파일 등 모든 테스트를 자동으로 진행하는가?"에 대한 답): 아니다. 어느 선택지든 실제 AI 호출과 실제 음성 시험은 CI에서 자동으로 돌지 않는다. CI에서 실제 유료 AI를 부르지 않는다는 규칙은 기술명세서 §10과 ADR-002에 이미 정해져 있다. 단위·계약·통합(컨테이너 DB)·시나리오(대화 전사 글을 넣고 가짜 GPT-Live·제브·분석 AI 사용, 음성 파일 없음)·장애 주입(가짜 AI)은 자동 실행할 수 있다. 음성 수동(실제 마이크·스피커)과 PoC·실제 AI 시험은 사람이 따로 실행한다. A는 PR마다 단위·계약·통합·ArchUnit만 돌리고 시나리오·장애 주입은 main 병합 뒤 매일 돌린다(PR 대기 짧음). B는 시나리오·장애 주입까지 PR마다 돌린다(일찍 잡지만 대기 김).

A. PR마다 단위·계약·통합·ArchUnit을 돌리고, 시나리오 하네스·장애 주입은 `main` 병합 뒤 매일 돌린다. 음성 수동·PoC·실제 AI 시험은 사람이 따로 돌린다
B. PR마다 단위·계약·통합·시나리오·장애 주입을 모두 돌린다
C. PR마다 단위 시험과 린트만 돌린다
D. Not yet defined
X. Other (please specify)

[Answer]: B

## Q9. 배포 방식

기술명세서는 EC2 1대에 수동 `deploy.sh`로 배포하고 자동 배포는 필수가 아니라고 적었고, 범위 정의에서 스테이징은 두지 않기로 했습니다. 작업 방식 기본값은 "병합하면 스테이징에 자동 배포, 운영은 별도 승인"이라 이와 다릅니다. 어느 쪽으로 확정할까요?

질문 중 확인(사용자 추가 질문 "Q9에 대한 의문사항. main 브랜치와 dev 브랜치가 별개로 존재하는가?"에 대한 답): 지금 정해진 방식에는 dev 브랜치가 없다. feature/{JiraKey}-설명 브랜치를 PR(리뷰 1명 + CI 통과)로 main에 병합 커밋으로 합치고(Q1·Q2, 기술명세서 §1.2·ADR-001), 배포 기준은 main이다. dev를 두면 feature → dev → main 구조가 되며, 기본 작업 방식의 '오래 유지되는 브랜치를 피한다' 원칙과 어긋나 이 프로젝트의 예외로 기록해야 한다.

질문 중 확인(사용자 추가 질문 "dev 브랜치를 설정하지 않았던 이유는?"에 대한 답): 빼기로 결정한 것이 아니라 참고 문서를 따랐다. ① 기술명세서 §1.2·ADR-001이 main과 feature/{JiraKey}-설명만 정의한다(확정 항목은 다시 묻지 않는 규칙). ② 배포 환경이 시연 서버 1대뿐이라(범위 Q6) dev에 대응할 서버가 없다. ③ PR 리뷰 1명 + CI(가짜 AI 시험 전부, 서비스별 커버리지 80%)가 main을 지킨다. ④ 4주 일정에서 dev↔main 맞추기가 추가 부담이고, 기본 작업 방식도 오래 유지되는 브랜치를 피한다. 시연 직전 고정은 dev 대신 main에 태그(예: demo-1105)를 붙여 배포하는 방법으로 할 수 있다.

A. 팀 결정대로 — 시연 서버(EC2 1대) 하나에 수동 `deploy.sh`로 배포하고 스테이징은 두지 않는다. 기본값과 다른 이 프로젝트의 방식으로 기록한다
B. `main`에 병합하면 시연 서버에 자동 배포한다(GitHub Actions)
C. Not yet defined
X. Other (please specify)

[Answer]: B

## Q10. 배포 실행·확인·되돌리기

수동 배포를 누가 언제 하고, 배포 뒤 무엇을 확인하며, 문제가 생기면 어떻게 되돌릴지 정해야 시연 당일 사고를 줄일 수 있습니다. 어떻게 할까요?

질문 중 확인(사용자 의견 "Q10 github action을 활용하여 자동배포를 하기로 결정하였는데, 해당 질문이 필요하지 않아 보임"에 대한 답): Q9=B(자동 배포)로 '누가·언제 배포하나'는 필요 없어졌다. 남는 것은 자동 배포 뒤 확인(헬스 체크)과 되돌리기 방법이며, 배포 파이프라인 단계(4.1)에서 정해도 늦지 않으므로 이 질문은 그 단계로 넘기는 것을 권했다.

C. 확인 단계 없이 배포만 한다(문제가 생기면 고치는 커밋을 다시 합쳐 배포)
D. Not yet defined
X. Other (please specify)

[Answer]: B

## Q12. 저장소 공개 여부
